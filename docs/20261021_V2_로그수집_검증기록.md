## 2. 핵심 요약

Alloy가 V2 namespace의 소유 표식이 있는 Pod 표준 로그(Alloy 자체 로그 제외)를 Kubernetes API로 읽고 Loki에 전달함. Grafana 관리자 인증으로 환경·서비스별 로그를 조회함. 노드 파일·앱 PVC 파일·Secret을 수집하지 않음. 기존 서비스와 자격 증명은 유지함.

## 3. 상세 내용

| 구성 | 설계 | 비고 |
|---|---|---|
| Loki | 3.7.9 단일 StatefulSet·filesystem/TSDB v13·전용 PVC2Gi | HA·외부 백업 아님 |
| 보존 | compactor24h·삭제 지연2h·WAL/marker 모두 PVC 경로 | 24시간 경과 삭제 실측은 별도 |
| Alloy | 1.21.0 단일 Deployment·로그 API·GA 기능 사용 | hostPath·특권·root 없음 |
| 수집 범위 | v2-dev/v2-verify/argocd/v2-observability의 OWNER 일치 Pod | Role은 namespace 단위이며 OWNER 필터는 수집 설정에서 적용 |
| 권한 | namespace별 pods get/list/watch·pods/log get | Secrets·exec·attach·nodes/proxy·다른 namespace 불허 |
| 접근 | Loki/Alloy ClusterIP·NetworkPolicy·Grafana 인증 | Loki 별도 사용자 인증 없음 |
| 네트워크 한계 | Alloy API443/6443은 포트 기준 허용 | API IP 변경 대응이며 외부 HTTPS 완전 차단 정책 아님 |
| 라벨 | cluster/namespace/environment/service/pod/container | 로그 본문·검색어·사용자 입력을 라벨로 넣지 않음 |
| 마스킹 | 전송 전 알려진 자격증명 형식에 정규식 적용 | best-effort, 모든 민감정보 차단 보장 아님 |
| 수집기 중단 | Alloy WAL 실험 기능 미사용 | 중단 중 손실·재수집 중복 가능, 정확히 한 번 전달 보장 없음 |
| 자원 | Loki128/512Mi·Alloy64/256Mi 요청/상한 | PVC 요청 용량이 호스트 물리 디스크 hard quota를 뜻하지 않음 |

### Grafana 사용

1. http://localhost:8083 에서 admin으로 로그인함. 비밀번호는 Git 제외 `.local/V2_로그인정보.md`를 확인함.
2. `V2 Logs` 대시보드에서 환경·서비스 필터를 선택함. 직접 주소는 http://localhost:8083/d/v2-logs 임.
3. `서비스 로그`에서 본문·시간·Pod를 확인하고 오류 관련 패널과 지표 대시보드를 함께 확인함.
4. Explore에서 Loki 데이터소스를 선택하고 아래 LogQL로 검색할 수 있음.

```logql
{cluster="ps-v2", environment="verify", service="book"}
{cluster="ps-v2", service="portal"} |~ `(?i)error|exception|traceback`
```

수집 대상은 stdout/stderr임. Portal의 PVC 내부 보안 이벤트 파일·호스트 journal·Kubernetes audit log는 포함하지 않음. 운영 로그 수집과 폐쇄망 신규 설치 검증은 이번 범위에서 제외함.

| 노드 메모리 | worker0 529Mi·worker1 1258Mi·server976Mi | 한 시점 관측이며 부하 상한 실증 아님 |

노드에서 들어오는 Loki `/metrics` 점검 요청에서 연결 종료 경고가 반복됨을 관측함. HTTP probe가 큰 응답을 일부 읽은 뒤 연결을 닫는 동작과의 관련성이 추정됨. 수집기 자신을 재수집하지 않는 정책에 더해 Loki liveness를 TCP 포트 확인으로 변경하여 점검 트래픽이 만드는 경고를 줄임. 애플리케이션 준비 상태는 `/ready`로 별도 확인하며 Prometheus는 `/metrics` 수집을 유지함.

로그 대시보드의 실제 조회 중 기존 Grafana384Mi 한도에서 OOMKilled1회를 확인함. Grafana 요청128Mi·상한768Mi 및 Go 메모리 목표512MiB로 조정하고 로그 패널·데이터소스 조회를300행·15초 갱신으로 제한함. 기존 지표 구성 포함 관측 namespace의 메모리 상한 합계는2816Mi로3Gi quota 이내임. 적용 후 Loki 재생성 시험과 분리해8회×3패널 backend query를 순차 실행함. 8회 모두 성공·동일 Pod UID·컨테이너 재시작0→0이며 샘플 메모리 최대305Mi를 확인함. 해당 단기 실습 조건의 결과이며 장시간·대규모 부하 안정성을 보장하지 않음. 첫 반복 시험의 마지막 조회는 의도한 Loki 재생성 시험과 중첩되어400으로 실패하였고, 그 결과를 정상 부하 통과 건수로 합산하지 않음.

최종 구현 대상은 `f7f54bcdc4503101953cede128b31d02b29dcefe`임. 구현 미참여 전문 검토자가 diff·원본·테스트46개·실제6marker/hash·마스킹·Grafana query/health·자원 설정·32개 자원 UID/Secret hash·권한·23개 target/10개 probe를 직접 대조함. 수집기 중지 중 재생성/영속 읽기는 구현자의 원본과 코드/회귀 테스트 순서를 대조한 것으로, 독립 재주입·재시작 건수로 합산하지 않음. PR #4 CI는46개 정적 테스트와 고정 바이너리 설정 검증을 통과함. 병합 후 main SHA 동기화와13개 Application 정상 상태는 별도 후속 확인 대상으로 관리함.

## 5. 확인 필요 사항

- compactor의 24h 설정과 실제 24시간 경과 자동 삭제는 구분함. 실제 시간 경과 삭제 검증은 미수행임.
- 전송 전 마스킹은 알려진 형식에 대한 방어이며 비밀값을 앱 로그에 출력해도 된다는 의미가 아님.
- API tail은 kubelet/API 부하를 추가하며 무손실·중복 없는 전달을 보장하지 않음.
- 노드 로컬 PVC의 Pod 재생성 보존과 다른 노드·다른 환경 백업 복원은 구분함.

## 6. 후속 조치

합성 로그 수집·마스킹·권한 거부·Pod 재생성 후 조회·기존 서비스 보존을 실측하고 독립 검토·PR·CI·병합·main 동기화를 수행함. 이후 사용자 직접 장애 진단 실습 또는 trace 계측 설계를 진행할 수 있음.
