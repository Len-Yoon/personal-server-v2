# V2 데이터·백업·복구 설계

## 1. 문서 정보

| 항목 | 내용 | 비고 |
|---|---|---|
| 작성일 | 2026-10-22 | Asia/Seoul |
| 기준 자료 | 사용자 승인, 현재 V2 배포 계약, PostgreSQL·Kubernetes 공식 문서 | 구현 증거 별도 |
| 목적 | 별도 API·PostgreSQL의 논리 백업과 빈 환경 복원을 검증함 | V1·N100 제외 |
| 상태 | 사용자 추천 설계 진행 승인 | 복제·HA·PITR 제외 |

## 2. 핵심 요약

기존 앱과 데이터를 보존하고 메모 CRUD API와 단일 PostgreSQL을 별도 namespace에 배포함. 매시간 논리 백업·최근24개 보관·맥북 반출·빈 복구 DB 반입·복원을 구현함. 백업 완료와 실제 복원 성공을 구분하며 데이터 일치·원본 보존·RTO/RPO를 실측함.

## 3. 상세 내용

| 항목 | 결정 | 비고 |
|---|---|---|
| 환경 | v2-data-dev / v2-data-restore | 동일 맥북 k3d, 물리 격리 아님 |
| 원본 | notes-api Deployment + postgres StatefulSet 1개 | API port8000, loopback8086 |
| 복구 | 별도 postgres StatefulSet 1개 + API replicas0 | 복원 검증 중만 UID 확인 후1, finally0 |
| 저장소 | 각 환경 DB1Gi·backup1Gi local-path PVC | Argo prune/delete 보호, 클러스터 삭제 시 손실 가능 |
| 계정 | postgres 초기화 / notes_owner DDL / notes_app notes DML / notes_backup SELECT | 서로 다른 실습 비밀번호, schema_version 앱 DML 금지 |
| 자격 증명 | Git 밖0600 파일과 소유 확인된 Secret | 누락·불일치 자동 교체 금지, bootstrap 계정 API에 미마운트 |
| API | 인증된 메모 CRUD, health/ready/metrics, 입력 제한·SQL parameter·transaction | synthetic 데이터만 초기 실습 |
| 백업 | pg_dump custom, 파일 잠금, 임시 기록 후 원자 게시, SHA256 manifest | 같은 이미지의 PostgreSQL17 도구 사용 |
| 일정 | 매시간 UTC, concurrencyPolicy Forbid, deadline300초, 파일락 | 수동 Job도 같은 락 사용, 성공24개 보관 |
| 반출·반입 | dev PVC→맥북0700디렉터리/0600파일→restore PVC | namespace 간 PVC 직접 공유 없음, 논리 dump64MiB 반출 상한 |
| 복원 | 고정 postgres-restore/notes_restore/notes_owner만 허용 | checksum 확인·빈DB검사·단일 transaction, owner/ACL 별도재설정 |
| 보안 | PSA restricted·전용SA tokenoff·기본deny·DB동일환경클라이언트만 허용 | DB TLS는 실습에서 미구성, 외부5432 공개 없음 |
| 정책 | 별도 고정 data namespace Pod VAP/CEL | 승인 digest·SA/token·자원 검사, 기존 앱 정책 유지 |
| GitOps | data-policy/data-dev/data-restore 3개 Application | 수동 sync, Secret은 외부 bootstrap |

복구 대상은 새 PVC·새 DB로 준비하며 초기 migration을 실행하지 않음. 복원 이후 notes 테이블만 앱에 DML 권한을 부여함. 생성된 백업에는 자격 증명·role password를 포함하지 않음. owner role·Secret은 선언된 초기화 절차로 별도 준비함.

## 4. 검토 결과

주 담당은 배포·초기화·반출·복구·검증 도구를 구현함. API 담당과 백업 담당이 별도 파일을 구현하고 독립 전문 검토자가 DB·보안·배포·정리 경계를 검토함. 같은 파일의 동시 수정은 하지 않으며 최종 수정은 주 담당에게 인계함.

## 5. 확인 필요 사항

| 항목 | 한계 | 비고 |
|---|---|---|
| RTO | 빈 DB 준비 후 restore Job부터 API와 데이터 확인까지 측정 | 설치·이미지반입 시간 제외 |
| RPO | 백업 이후 marker 미복원·snapshot 시작~종료 창 확인 | 정확 snapshot 시각과 동일하지 않음 |
| 백업 주기 | 1시간은 목표 | 맥북 절전·Job실패·수동실행 등으로 보장되지 않음 |
| 장애 영역 | PVC와 호스트 반출이 같은 물리 장비에 있음 | 외부재해복구·물리HA 아님 |
| 스토리지 | local-path는 노드 종속·정적소형 용량 | 다른 노드 재스케줄링/디스크풀에 대한 HA 아님 |
| 반출 한도 | custom dump64MiB | 메모리 기반 반출, 상한 초과 시 거부 |
| 공급망 | base digest·의존성버전·실행image digest 고정 | apt/PyPI 완전오프라인·서명 검증은7단계 |

## 6. 후속 조치

실제 이미지 빌드·Argo 적용·백업/복원·권한·데이터 보존·독립 검토·CI·병합 후 검증을 수행하고 별도 기록함. 최초 복원은 빈 DB에만 허용하며 복원된 DB를 자동 초기화하지 않음.
