## 2. 핵심 요약

V1에서 개발한 **Portal·Book·YouTube 세 앱의 고정 소스**를 재사용해 맥북 전용 V2 실습 환경을 구성함. 앱 실행에 Argo CD 기반 배포 관리, 지표·로그·요청 추적, 접근 권한·통신·배포 정책을 연결하고, 별도 메모 API와 PostgreSQL을 추가해 백업·복원을 검증함.

V1에도 K3s·Prometheus·Grafana·CI·백업 구성이 존재함. V2는 이 기반을 별도 실습 환경에 재구성하고 GitOps·관측 연계·정책 집행·재현 가능한 장애 실습을 확장한 프로젝트임. 기존 운영 서비스를 V2로 이전하거나 V1 전체를 복제한 것은 아님.

공유용 설명 문구:

> V1 개인 서버에서 개발한 Portal·Book·YouTube를 기반으로 맥북의 별도 Kubernetes 실습 환경을 구축함. Argo CD로 앱과 플랫폼 설정을 Git에서 관리하고, Prometheus·Grafana·Loki·Alloy·OpenTelemetry·Tempo를 연결해 지표·로그·요청 흐름을 확인하도록 구성함. 서비스별 권한·통신·배포 정책과 별도 PostgreSQL 백업·복원 실습을 추가하고, 자동 검증·독립 검토·로컬 실행으로 동작과 데이터 보존을 확인함.

## 3. 상세 내용

### 3.1. V1에서 가져온 것과 V2에서 제외한 것

| 구분 | 내용 | 비고 |
|---|---|---|
| 재사용한 앱 | Portal의 파일함·통합 검색, Book의 책·메모, YouTube의 영상·메모 | 고정 V1 커밋의 소스만 추출 |
| 재사용 방식 | 앱 소스를 ARM64 실습 이미지로 다시 빌드하고 digest로 고정함 | 앱별 source/archive/patch 기록은 `apps/images.lock.json` |
| V2 전용 조정 | localhost·내부 서비스 주소, 개발/검증 쿠키 구분, HTTP 요청 계측 | 이미지 빌드 과정의 V2 패치, V1 원본 수정 없음 |
| 데이터 | 앱별 새 PVC·합성 샘플·실습 자격 증명을 사용함 | 운영 DB·업로드 파일·Secret 복사 없음 |
| 제외한 서비스 | Crawler/뉴스 수집, 차량관리, SystemAgent, HomeOps 실행기, 운영 Telegram 연계 | V1의 모든 기능이 V2에 연결된 것은 아님 |
| 실행 환경 | V1은 고정 자료상 N100·WSL2의 K3s/Compose 운영 구성, V2는 맥북 로컬 k3d | N100에 V2를 배포하지 않음 |

### 3.2. V1을 기준으로 V2에 붙인 구성

아래 V1 열은 고정 커밋의 원본 자료 기준임. V1의 현재 운영 성공 여부를 새로 확인한 결과와 구분함.

| 영역 | V1 기준 구성 | V2에서 수행한 작업 | 목적·비고 |
|---|---|---|---|
| Kubernetes 환경 | N100·WSL2의 K3s와 Compose를 역할별로 운영함 | 맥북에 별도 k3d server1·worker2, 개발/검증 namespace를 구성함 | 운영 보호·스케줄링 실습, 물리 HA 아님 |
| 앱 배포 | GitHub Actions 검사·배포 분류·승인된 대상 반영 절차가 있음 | Kustomize 앱 명세와 Helm 플랫폼 명세를 Argo CD Application으로 관리함 | Git 선언과 실제 상태 비교·수동 sync·drift 및 실패 배포 복구 |
| 서비스 연결 | Portal이 서비스별 검색 API를 호출함 | dev/verify 각각 Portal→Book·YouTube 검색·링크를 연결함 | 환경별 데이터·인증·통신 분리 |
| 지표 | Prometheus·Grafana·Alertmanager·Relay·Telegram 구성이 있음 | V2 Prometheus·Grafana·Blackbox를 구성하고 앱 HTTP·Kubernetes·Argo 상태를 관측함 | V2 내부 경보 확인, 외부 Telegram 전달은 미구성 |
| 로그 | V1 README에 Loki 격리 샘플 실습이 기록돼 있음 | Alloy로 대상 Pod 로그를 수집해 Loki에 저장하고 Grafana에서 환경·서비스별 조회함 | 표준 Pod 로그·전송 전 마스킹, 호스트 전체 로그 수집 아님 |
| 요청 추적 | Portal이 Book·YouTube 검색 API를 HTTP로 호출함 | 세 앱 dev/verify에 OpenTelemetry 계측을 추가하고 Alloy→Tempo→Grafana를 연결함 | Portal→Book/YouTube의 부모·자식 span과 같은 요청의 로그 연결 |
| 권한·Secret | 기존 앱 인증·이미지 보안·운영 대상 제한이 있음 | 전용 SA·진단 RBAC·토큰 자동 마운트 차단·로컬0600 파일/Secret 불일치 시 중단을 적용함 | 앱·진단·관리자 권한 구분, 인증값 Git/로그 제외 |
| 통신·배포 정책 | V1 README는 운영 통신 차단 정책을 미적용으로 기록함 | 기본 통신 거부와 필요한 경로만 허용하고 PSA·내장 VAP/CEL로 Pod/앱 설정을 검사함 | 환경 간 접근·오설정 배포의 허용/거부 실증 |
| 자원·장애 | V1은 실제 서비스 상태 검사·제한형 복구를 관리함 | requests/limits·Quota·LimitRange와 이미지 누락·Pending·OOM·Probe·worker 장애 실습을 구성함 | 정상 실행뿐 아니라 실패·이벤트·복구를 검증 |
| 별도 DB 실습 | 기존 앱은 SQLite·JSON·파일을 사용함 | V2 전용 메모 CRUD API와 PostgreSQL StatefulSet·PVC를 새로 작성함 | 기존 세 앱의 SQLite를 교체하지 않음 |
| 백업·복원 | timer·Job·암호화 Google Drive 사본과 격리 복원 구성이 있음 | PostgreSQL 논리 백업 Job/CronJob·24개 보관·checksum·맥북 반출·빈 DB 복원을 구현함 | V2는 같은 맥북의 로컬 복원 실습, 원격 재해복구는 미구현 |
| 검증 | V1 서비스·운영 도구의 회귀·CI·보안 검사가 있음 | V2 안전 경계·계측·권한·백업 계약 테스트와 실제 로컬 허용/거부·보존 검증을 추가함 | CI 성공·병합·로컬 배포·실행 성공을 각각 기록 |

### 3.3. 연결 후 사용 흐름

| 흐름 | 연결 순서 | 확인할 수 있는 내용·비고 |
|---|---|---|
| 앱 요청 | 브라우저 → V2 Portal → 같은 환경의 Book·YouTube | 서비스별 검색 결과와 부분 실패 |
| 배포 | 기능 브랜치 → 테스트·검토 → PR·CI → main → Argo 수동 sync | Git 변경과 배포 상태, CI가 로컬 클러스터를 자동 배포하지 않음 |
| 지표 | 앱/Argo/Kubernetes 상태 → Prometheus·Blackbox → Grafana | 가용성과 자원 상태 |
| 로그 | 대상 앱 Pod 표준 로그 → Alloy → Loki → Grafana | 환경·서비스별 로그와 trace ID 연계 |
| 추적 | 앱 HTTP span → Alloy OTLP → Tempo → Grafana | 하나의 검색 요청이 거친 서비스·구간 |
| 데이터 복원 | 별도 메모 API → PostgreSQL → 논리 백업 → 맥북 반출 → 별도 DB 복원 | 데이터 일치·복구 후 API·원본 보존 |

새 메모 API는 기존 세 앱과 별도 서비스임. `/health`, `/ready`, `/metrics`를 제공하지만 기존 세 앱의 통합 로그·trace·Prometheus 수집 대상에 모두 추가한 것으로 표현하지 않음.

## 4. 검토 결과

V1 고정 커밋의 README, V2 코드·이미지 잠금·단계별 검증 기록, 최근 main 상태 및 격리 실습 JSON을 대조함. V1에도 있던 Kubernetes·지표·CI·백업을 V2에서 처음 도입한 것으로 쓰지 않도록 구분함. 과거 단계의11개 Application·13개 target 등은 해당 시점의 기록으로 유지하고 최신 요약은18개·24개로 구분함.

이번 작업은 기능·CI·배포 명세를 변경하지 않는 문서 정리이므로 주 담당1명이 원본·링크·상태·비밀값 제외를 자기 검수함. 하위 에이전트는 사용하지 않음. 기존 기능 구현의 독립 검토와 이번 문서 자기 검수를 합산하지 않음.

## 6. 후속 조치

1. 폐쇄망 구현은 보류하고 현재 V2 환경의 직접 운영 실습을 우선함.
2. 정상 상태 확인 → Pod·이벤트·로그 진단 → 격리 장애 복구 → 빈 DB 복원 순서로 직접 실행 결과를 기록함.
3. 향후 개발은 필요한 목표와 성공 기준을 확인한 뒤 범위를 결정함.
