## 1. 문서 정보

| 항목 | 내용 | 비고 |
|---|---|---|
| 작성일 | 2026-10-22 | Asia/Seoul |
| 기준 자료 | main879e1e5·현재 V2 API·고정 앱 소스23572de·Kubernetes 공식 문서 | 원본·실측·계획 구분 |
| 목적 | 정상 기능 유지와 금지 작업의 실제 거부를 검증함 | 개발계획5단계 |

## 2. 핵심 요약

기존 PSA와 NetworkPolicy를 보완하고 Kubernetes 내장 ValidatingAdmissionPolicy/CEL로 잘못된 앱 배포를 거부하는 방식을 추천함. 새 정책 엔진이나 외부 Secret 서버는 추가하지 않음. 앱별 ServiceAccount·최소 진단 권한·Secret 취급 도구·통신 경계·자동 거부 및 복구 검증을 하나의 단계로 구현함.

기존 비밀번호와 PVC 데이터를 유지함. Book의 외부 도서 검색은 명시한 비공인 대역을 제외한 IPv4 HTTPS 예외로 보존하고, 개발·검증 환경의 사설 통신은 차단함. 따라서 이번 단계를 폐쇄망 완성으로 표현하지 않음.

| Pod 보안 | dev/verify/observability namespace에 restricted:v1.35 적용 | 새 기능으로 재계산하지 않음 |

### 3.3 적용 경계와 순서

1. 기존 앱·PVC·Secret UID/hash·샘플·14개 Argo 앱·24개 Prometheus target을 기준으로 저장함.
2. 정책은 확정 namespace 이름 v2-dev/v2-verify에만 매칭함. 제거할 수 있는 앱 owner label을 정책 적용 조건으로 사용하지 않으며 owner 누락 자체를 위반으로 검사함.
3. 현재 앱 Deployment 템플릿과 최종 Pod를 검사함. 다른 controller는 최초 명세 접수와 최종 Pod 거부가 다를 수 있음을 구분함. status/scale 하위 리소스를 무차별 차단하지 않음.
4. 전용 SA/RBAC·호환 명세를 먼저 적용하고 정상 workload의 server dry-run을 확인함. VAP는 Warn/Audit로 먼저 확인하고 검증된 동일 범위를 Deny로 전환함. API discovery만으로 실제 enforcement를 주장하지 않음.
5. 통신 정책은 기존 허용 경로를 선언한 뒤 기본 거부를 적용함. 양방향 격리와 허용 연결을 실제 패킷으로 검증함. node/kubelet 또는 localhost port-forward 경로를 Pod 간 격리 증거로 사용하지 않음.
6. 실습용 Pod는 기존 Service의 app.kubernetes.io/name=book/portal/youtube selector와 겹치지 않는 v2-security-probe 식별자를 사용함. 별도 진단 SA·tokenoff·고정 V2 이미지의 승인된 검증 Pod를 정책에서 명시 허용하며 Service 트래픽 유입을 검사함.
7. 실패 시 소유/UID가 확인된 이번 Binding만 일시 해제하고 Git 명세를 수정·재적용함. API 서버 전체 보안 기능 해제나 무조건 fail-open을 복구 방법으로 사용하지 않음.
8. 독립 전문 검토·CI·PR·병합 후 main 수동 동기화와 기존 서비스 회귀를 완료함.

IPv4 HTTPS 예외는 구현 시 정확한 CIDR 목록을 코드·문서·테스트에 고정함. RFC1918 외에100.64.0.0/10·198.18.0.0/15 등을 포함하며, 이 목록을 완전한 도메인/Internet 보안 경계로 표현하지 않음. node-local/hostNetwork·DNAT 관련 NetworkPolicy 한계는 실제 Pod 통신 검증과 구분함.

LimitRange는 누락한 requests/limits를 기본값으로 채울 수 있으므로, 최종 객체에 자원 값이 존재하는 검증과 사용자가 원본에서 명시한 검증을 혼동하지 않음. 이미지 digest 고정은 서명·출처 신뢰 증명이 아니며 서명 검증은7단계에서 다룸.

### 3.4 관측·관리 영역의 예외

| 경계 | 이번 방침 | 비고 |
|---|---|---|
| Argo 관리자·controller | 기존 관리 권한 유지, 앱 정책 강제 대상에서 제외 | 관리자 신뢰 경계를 앱 최소 권한과 구분 |
| Argo Redis/repo-server token | API 불필요 여부와 chart 호환성 확인 후 불필요 마운트만 제거 검토 | self 관리·현재 접속을 깨는 일괄 강제 금지 |
| 관측 API 권한 | Alloy/Prometheus/kube-state-metrics의 필요한 권한·토큰 유지, 금지 API 범위 회귀 | 광범위 Secret/exec 권한 신규 부여 없음 |
| Alloy443/6443 | 기존 API DNAT 대응 예외 유지 | 외부 HTTPS 전체 차단 완료로 표현하지 않음 |
| Secret 저장 | V2 실습 Secret·로컬 파일 보강 | 저장소 암호화·외부 Vault·운영 Secret 관리 완료로 확대하지 않음 |
| 접근 주체 | 앱 계정·제한된 진단 계정과 로컬 관리자를 구분 | 현재 관리자 kubeconfig 자체가 읽기 전용이 되는 것은 아님 |

## 4. 검토 결과 및 검증 계획

| 검사 | 허용 | 금지·실패 조건 |
|---|---|---|
| RBAC | 진단 계정의 같은 환경 pods/events/logs | Secret·타 환경·exec·write·RBAC 변경·token 발급 |
| 앱 API | 앱 요청·기존 마운트 Secret 사용 | 앱 SA로 Secret 조회·exec·cluster API 관리 |
| 네트워크 | Portal→같은 환경 Book/YouTube, DNS, Alloy, 관측 probe | dev↔verify, Book/YouTube→Portal 등 허용하지 않은 사설 경로 |
| admission | 올바른 소유·SA·tokenoff·고정 이미지의 Pod/Deployment | privileged·hostPath·미고정 tag·타 registry·tokenon·잘못된 SA·owner 제거·UPDATE 우회 |
| Secret 도구 | 정상 파일/기존 Secret 보존 | 기존 Secret이 있는데 로컬 파일 유실/불일치, symlink·노출 권한 |
| Secret 교체 | 별도 canary만 UID/내용 readback 확인 | 기존 인증 값 출력·일괄 변경·Git 저장 |
| 회귀 | 검색·로그인·샘플·지표·로그·trace·localhost | 기존 UID/hash·데이터 손상, 정상 요청/수집 경로 차단 |
| 복구 | Binding UID guard·재적용·정상과 금지 재검증 | 광역 삭제·운영 context·기본 context 사용 |

RBAC의 실제 API 거부 검증에는 필요 시 유효시간을 제한한 진단용 TokenRequest를 메모리에서만 사용하고 토큰 값·응답 Secret 본문을 출력/저장하지 않음. `auth can-i` 판정과 실제 인증된 API 응답을 구분함. admission 거부는 server dry-run으로 안전하게 확인하며, 이것을 Pod 실행·네트워크 실증으로 확대하지 않음.

주 담당(root)은 현황·설계·검증 통합을 맡고 독립 보안 담당(review)은 원본과 실행 경계·정책·negative gate를 읽기 전용으로 검토함. 같은 파일 동시 수정은 하지 않음. 독립 검토에서 지적한 외부 예외 CIDR의 표현과 검증 Pod의 Service selector 충돌 방지를 설계에 반영함. 구현 시에는 정책/권한 담당과 CLI/검증 담당을 분리하고 최종 검토자는 구현에 참여하지 않음. 이번 조사에서는 파일·클러스터·CI 구성을 변경하지 않았으며 이 설계 문서만 작성함.

## 5. 확인 필요 사항

- 사용자 확인 대상은3.2~3.4 추천 범위이며 특히 Book 외부 HTTPS 유지·앱 namespace에 한정한 정책 집행을 포함함.
- Book HTTPS 예외의 실제 CNI/DNAT 동작·도서 검색 회귀는 구현 후 확인 필요함. 정책 엔진의 API 존재만으로 정책 작동이 검증되지는 않음.
- 폐쇄망 설치·외부 의존성 제거·서명 검증·다른 호스트 복원은 이후 단계임.
- app SA의 Secret API 거부가 관리자나 Pod 생성 권한자의 Secret 마운트까지 막는 것은 아님. 진단 Role에는 Pod 생성 권한을 부여하지 않음.

## 6. 후속 조치

이 추천 범위를 확인받은 뒤 구현·관련 검증·독립 전문 검토·기능 브랜치 push·PR·CI·병합·병합 후 V2 main 동기화를 수행함. 같은 범위의 단계별 재승인은 요청하지 않음.
