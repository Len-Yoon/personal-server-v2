## 2. 핵심 요약

메모 API의 업무 요청 수·5xx·4xx·응답 시간 histogram을 Prometheus에 연결하고 Grafana 전용 대시보드를 추가함. 상태 점검 요청은 업무 지표에서 제외함. 배포 준비는 전체 테스트 → 변경 소스만 ARM64 빌드·로컬 등록 → digest 검증 → dev/restore/정책/lock 갱신을 한 명령으로 수행하도록 보강함. Git push·PR·병합·Argo Sync는 기존 검토 경계를 유지함.

코드·실행 증거·CI·실제 배포·짧은 정상 상태 유지 관측을 구분함. 이 문서의 초기 구현 시점에는 최종 배포·안정화 결과가 미확정이며, 검증 완료 후 결과 표를 갱신함.

## 3. 상세 내용

### 3.1. 관측 범위

| 항목 | 구현 내용 | 비고 |
|---|---|---|
| 업무 요청 | v2_notes_api_requests_total | /notes 및 /notes/ 하위 경로, 실패·잘못된 하위 경로 포함 |
| 오류 | v2_notes_api_errors_total, v2_notes_api_client_errors_total | 5xx·4xx 분리, 401/422/413도4xx에 포함 |
| 응답 시간 | v2_notes_api_duration_seconds histogram | 응답 본문 완료까지 서버 처리 시간, 클라이언트 전체 왕복 시간 아님 |
| 개인정보 제한 | URL·UUID·query·본문·인증값·사용자 label 없음 | 고정 bucket의 le label만 사용 |
| 기존 지표 | 기존 requests/errors/uptime 유지 | 기존 전체 요청 지표에는 probe가 포함되므로 업무 대시보드에서 구분 |
| Prometheus | notes-api 직접 scrape1개, Blackbox health/ready2개 | 기존24개에서 총27개 대상 예상, 복구 API0은 수집하지 않음 |
| Grafana | v2-notes-api 대시보드8패널 | 수집·가용성·RPS·5xx비율·4xx·p95·평균·가동 시간 |
| 통신 | dev의 기존 관측 namespace 전체 허용을 owner+Prometheus/Blackbox Pod로 축소 | TCP8000 허용이며 HTTP 경로 단위 통제는 아님 |

[Grafana 메모 API 대시보드](http://localhost:8083/d/v2-notes-api) 및 [앱 버전](http://localhost:8086/version)은 V2 포워딩 실행 중 접속함. 요청이 없으면 지연 평균·분위수는 No data가 될 수 있으며, Pod 재시작 시 프로세스 counter가 초기화됨. 백분위수는 고정 bucket을 사용한 추정값임. [Prometheus histogram](https://prometheus.io/docs/practices/histograms/)과 [텍스트 형식](https://prometheus.io/docs/instrumenting/exposition_formats/)을 기준으로 구현함.

### 3.2. 배포 준비 자동화

저장소 루트에서 전체 테스트 의존성이 설치된 Python 실행기를 사용함. 기존 로컬 검증 환경 예시는 다음과 같음.

```sh
.local/otel-venv/bin/python tools/prepare_data_release.py
```

| 단계 | 성공 기준 | 비고 |
|---:|---|---|
| 1 | V2 kubeconfig·context·소유 확인 및 동시 실행 잠금 | N100·원격 Docker 주소 입력 없음 |
| 2 | 전체 테스트 통과·skip0·빈 suite 거부 | 설치 의존성 부족을 성공으로 숨기지 않음 |
| 3 | 소스 해시 변경 이미지에 한해 빌드·등록 | 변경 없는 Postgres는 재빌드하지 않음 |
| 4 | linux/arm64·RepoDigest·고정 loopback registry 실제 manifest SHA256 대조 | 임의 registry·tag를 배포 참조로 허용하지 않음 |
| 5 | 소스 race·명세 race 감지 후 dev/restore/정책/lock 함께 갱신 | 기존 호출 build_data.py도 유지하나 전체 테스트는 prepare 도구로 실행 |
| 6 | 같은 소스·명세 재실행 시 내용 변경 없음 | 재사용 이미지도 실제 registry 검증 |

테스트·빌드·push·digest 검증 실패 시 추적 명세를 갱신하지 않음. 파일 교체 도중 처리 가능한 예외는 이전 파일로 복귀함. 이미 push한 이미지 layer의 제거는 수행하지 않으며 Git 명세만 보존함. SIGKILL·전원 종료·OS 장애에서 다중 파일의 완전 원자성을 보장하지 않으므로, 중단 후에는 `git diff`와 lock/정책 일치를 확인한 뒤 재실행함. GitHub 실행기에서 맥북 localhost registry에 접근시키지 않음.

### 3.3. 배포 및 안정화 확인

이미지·명세를 PR·CI·독립 검토 후 병합하고 다음 순서로 Argo에 적용함. 실제 명령의 revision은 적용할 커밋의40자리 SHA임.

```sh
REVISION=$(git rev-parse HEAD)
python3 tools/lab.py sync data-policy --revision "$REVISION"
python3 tools/lab.py sync data-dev --revision "$REVISION"
python3 tools/lab.py sync data-restore --revision "$REVISION"
python3 tools/lab.py sync prometheus --revision "$REVISION"
python3 tools/lab.py sync grafana --revision "$REVISION"
```

이미지 정책→앱 전환 사이에는 이전 이미지 Pod 재생성이 거부될 수 있으므로 연속 Sync함. 복귀는 코드·lock·dev/restore·정책 및 관측 명세를 함께 되돌린 검토된 Git 커밋을 같은 순서로 적용함. API 변경에는 스키마 변경·DB 복원·PVC 삭제를 포함하지 않음. 복구 API는 replicas=0을 유지함.

검증기는 `tools/verify_notes_observability.py`임. 배포 전 `--baseline`으로 보존 기준을 기록하고(기존 기준 덮어쓰기 거부), 배포 후 포워딩을 유지하면서 기본180초 검증을 수행함. 새 지표·대시보드 준비 시간은 정상 상태 유지 관측 시간과 구분함.

```sh
# 배포 전 최초 기준 수집. 이미 기준이 있으면 자동 덮어쓰지 않음.
python3 tools/verify_notes_observability.py --baseline
# 별도 터미널에서 python3 tools/lab.py serve 유지
python3 tools/verify_notes_observability.py --soak-seconds 180
```

읽기 요청과 의도한401/422 요청만 생성함. 실제 PromQL과 Grafana8패널 backend 수치 프레임,27개 scrape/HTTP probe,18개 Argo 상태,Pod UID·재시작 횟수 불변,원본5행/복구4행 전체 해시·PVC·Secret·기존 서비스 보존을 대조함. Grafana 인증 요청은 고정 loopback으로 제한하고 프록시·리디렉션을 사용하지 않음.

## 5. 확인 필요 사항

- 안정화 관측은 소량의 읽기 요청을 사용한 짧은 맥북 실습임. 장기 운영 안정성·부하 용량·SLA·물리 HA의 증거로 확대하지 않음.
- notes-api 로그·trace 통합이나 외부 알림 수신까지 추가한 것으로 표현하지 않음.
- Terraform·폐쇄망·SBOM·서명·N100 이전·별도 환경 전체 재해복구는 이번 범위에서 제외함.
- 사용자 직접 학습과 운영 명령 수행은 고도화·안정화 이후 재개하며 현재 완료로 표시하지 않음.
